# Legacy webskillcomposition — audit of our share

As of: 30.10.2026. Examined was what our group contributed in the university repo `webskillcomposition` on branch `Ungetestet` (`5812275`) relative to `dev` (`d824975`) — comparison `origin/dev..Ungetestet`.
Code that was already in `dev` is only reported (column "dev?"), not evaluated and not changed.

This document replaces the WSC parts of [`legacy.md`](legacy.md) (section B) and [`legacy-dead-code.md`](legacy-dead-code.md) (IDs W…); their open points have been re-checked and carry the old ID here in the column "ex-ID". Counterpart for this repo: [`legacy-cell.md`](legacy-cell.md). Plan: [`work-plans/cleanup-and-code-handbook.md`](cleanup-and-code-handbook.md).
What each file does is described in [`README.md`](../code/README.md) (part B: `code/webskill-*.md`).

**Cleaning up is done on branch `ADP_Lokaliserung`** (webskillcomposition, local, unmerged). What has been implemented is at the end under "Implementation status".

**Method:** TypeScript compiler API (import and symbol graph with reachability from `main.tsx` and `tag-tool/main.tsx`, without tests), `tsc --noEmit --noUnusedLocals --noUnusedParameters`, Python AST for the backend, hash comparison of about 1,800 function bodies, search for identical blocks from 6 normalised lines, assignment of the lines via blame, grep only over our added lines. Purely static — "unused" (ungenutzt) means: no user found in the code, no dynamic access recognisable.

**Test baseline:** `tsc` error-free; `vitest run` 79 files / 836 tests green; backend `pytest` 81 passed, 1 skipped.

**Confidence:** certain = symbol graph and grep without user; probable = user only indirect or time-bound; uncertain = intent unclear.

## 0. Structural finding S1: revert 839857c distorts the diff
Commit 839857c (Shaming Zhang, 28.10.) undoes the merge `origin/dev -> UngetestetAR`, **without dev dropping out of the history**. Therefore dev is formally included, but dev changes are missing in content. Consequences in the diff:

- 23 further files are mixed (applicationController.ts, store.ts, server_connection.py ...).
- Blame of the approx. 51,800 changed lines: NobbisCode 17,042, Meric-L 15,764, Shaming Zhang 9,416, John Glanz 5,380, **Revert 4,197**, dennis 17.
- In the tables, such findings show `Revert` in the column "dev?": report only, do not change.
- **Classification (coordinator, 30.10.):** The revert is intended. ### 3. Error propagation

#### 3a) Reference of robot base and module

**Layer 1 (ceiling camera, Pi).** `localize_camera` forms `T_world_cam` once per image from **all** visible world tags of the tag map (`localize.py:184-239`; with >= 2 tags and calibration one shared PnP over all tag corners, `:213-221`, `pose.py:272-321`). Robot and modules then go through the same formula `T_world_cam · T_cam_tag · tag_to_module` (`localize.py:302-306`). "Nearest world tag" is reported in layer 1 only as an **addition** (`reference_tag_id`, `poseInReferenceTag`, `:311-316`; `primary_tag_id`, `:233`). The frontend does not evaluate either (search for `referenceTag|poseInReferenceTag` in WSC: no use apart from name duplicates). Robot and module therefore refer in layer 1 to **the same** camera estimate. Position errors of individual world tags enter there only via the adjustment of the PnP in `T_world_cam`, not differently per object.

**Layer 2 on the Pi.** Anchor: world tag = `nearest_world_tag(tag_map, request.robot_base)` (`plan.py:283-292`), a single tag of the **hand-Pi tag map**. Then `T_world_base` from this tag (`handeye.py:114-124`); modules are planned and measured with the anchored base: `T_world_module = T_world_base · F · X · C`. Robot→module is then only `F·X·C`; the world-tag position cancels (`inv(T_world_base)·T_world_base`). The **rough first look** however uses the layer-1 world of the ceiling Pi from the request (`layer2.ts:150-185`), and that can differ from the hand-Pi tag map (3c-3).

**Layer 2 in the frontend** (`ApproachPlanPanel`, included in `AutolocateActions.tsx:3`): base = anchor world-tag position **from the catalog** (`ApproachPlanPanel.tsx:584-596`, `tagServo.ts:198-213`); modules = layer-1 world of the ceiling Pi. These are **two different references**: robot relative to a single world tag in the catalog world, module relative to the Pi world (fit over all tags). Errors in the tag-map position of this tag and any catalog-vs-Pi deviation go **directly into robot→module**.

#### 3b) Rigid body, rotation, scale

- **Rigid-body offset** of `T_world_cam` (layer 1): cancels exactly in `inv(T_wr)·T_wm`, as long as `T_world_cam` is one single value for both (`E·T_cr`, `E·T_cm`, `E` cancels out). Holds Pi-internally.
- **Rotation error** of `T_world_cam`: also cancels arithmetically, **but no longer in the frontend**: `levelModulePose` (`cellModules.ts:172-184`), `robotOriginFromBase` (`layer2.ts:205-226`), `baseCorrection` (`tagServo.ts:203-212`) and `usePickPlaceRun.ts:329-337` keep only the **heading** and discard the tilt ("its tilt is noise"). A residual tilt of `E` (e.g. from the position of 585 with z = 0.17 m and pitch -2.5 deg) thereby stays on the position side, while the orientation is cut off. Lever arm: about 17 mm per degree per metre of robot-module distance. This is the structure of the calculation, not a measured value; the actual size is **uncertain**.
- **Different references** (catalog world tag vs. Pi fit): offset = catalog position minus Pi position of the anchor tag, **not** compensated (3c). Today 0 for anchor 583, up to approx. 2 m for 586.
- **Scale / tag size:** The distance T_cam_tag scales linearly with `assumed_size/true_size` (`tagmap.py:143-150`; doc `apriltag-tagmap-over-opcua.md`). The world-tag size enters (i) into the corners of the ceiling PnP (`pose.py:314-316`): corner offset per corner 1 mm at 0.198 vs. 0.2, negligible; (ii) into the **map survey itself** (`place_tags`, `tagmap.py:425-455`): distances from co-observations scale with the assumed size, 1 % is 2 cm at 2 m; (iii) into every single-tag localisation, especially in the hand-Pi anchor (`apriltag.py:1196-1210`): camera-tag distance scales 1:1, at a 1.0 m anchor standoff (`approachPlan.ts: DEFAULT_ANCHOR_STANDOFF_M = 1.0`) that would be 10 mm per 1 % size error, at 0.3 m (`plan.py: DEFAULT_STANDOFF_M`) 3 mm. This enters the base directly via `T_world_base`. The frontend constant 0.198 (`moduleCatalog.ts:428-429`) has **no** effect on measurements, only on markers/bounds: the frontend never sends a size to the Pi (`measureTagsCall.ts` sends only `tagIds` and `frames`).

#### 3c) Mixing of sources

Evidenced:

1. **Frontend anchor**: base from catalog world-tag position (`ApproachPlanPanel.tsx:584-596`) against modules from Pi layer 1 (`ApproachPlanPanel.tsx:254`, `approachPlan.ts:90-110`). The offset hits only the base. Today for tag 583 harmless (positions equal), for 584-586 wrong by 0.5-2 m. Mitigating: `anchorCandidates` sorted by `seen` from `worldTagCheck.deviations` (`ApproachPlanPanel.tsx:169-175, 254`; `approachPlan.ts:136-139`); probably the tag with the smallest deviation comes first, i.e. 583. **uncertain**: I did not trace the sorting in `worldTagCheck`/`ApproachPlanPanel.tsx:169-175` in detail.
2. **Catalog orientation 0 vs. Pi rotation**: the base yaw comes from `yawOf(tagInWorld · inv(tagInBase))` with the catalog rotation (`tagServo.ts:203`) and is thereby distorted by the catalog-vs-Pi rotation difference (magnitude for yaw **uncertain**).
3. **Two Pi tag maps** (ceiling Pi, hand Pi): the request contains the layer-1 world of the ceiling Pi, the anchor uses the file of the hand Pi (`plan.py:283-290`). Equality of both files is enforced nowhere. **uncertain** whether both Pis have pulled 3e54cd6.
4. **Pick & place**: `baseInWorld` = twin origin (`usePickPlaceRun.ts:325-337`), `table` = scene module (layer 1 rough or layer 2 precise). After a new layer-1 scan "precise" modules are kept (`mergeLayer1Scan`, `cellModules.ts:463-480`), but the robot base comes anew from layer 1, and the anchor correction is discarded (`ApproachPlanPanel.tsx:178-184`). Table (anchor world) and base (layer-1 world) then stand in different worlds. The mechanism is evidenced in the code; whether it occurs in operation depends on the sequence (**uncertain**).

#### 3d) Does the world enter direct operation?

- `tagInBaseFrom = F · X · C` (`tagServo.ts:100`) and `servoStep` (`:132-178`): **world-free**. The target comes from `poseInCamera` of the hand camera, flange from URDF FK. The world enters only if the tag is not in the image.
- **First look** (approach, standoff 0.35 m or 0.6 m): `tagInBase = inv(baseInWorld)·tagWorld` (`approachPlan.ts:90-110`; Pi: `plan.py:203-208`). On this path the world error (3c-1/-3) sends the robot off target; `MAX_STEP_M = 0.05` (`tagServo.ts`) limits the correction per step to 5 cm. **uncertain**: whether several steps suffice depends on the field of view.
- **Pick & place** (`pickPlace.ts:137-143, 312-322, 770`): target points from `inv(baseInWorld)·poseOf(table)`. Here the world is the **basis of the calculation**, not just a starting approximation. The error from 3c-4 goes into the target position without hand-camera correction (unless the corner is measured, `measurePlaceFromCorner`, `usePickPlaceRun.ts:515-520`).
- **Collision check** `cellClearance.ts:25,56,111`: floor = `bounds.min[2]` of the table, i.e. relative to the table. No world-tag reference found.
- **Safety distances** (standoff, `MAX_STEP_M`): constants, world-free.

Conclusion: "With direct measurement the world plays no role" holds for `F·X·C`. But operation does not consist only of that: target specification and pick & place calculate in world coordinates, and there the base partly comes from a **different world** (catalog world tag) than the modules. A world-tag offset is a harmless common offset only if base and module run through **the same world transformation**. That is exactly not the case for the frontend anchor.

Diff of 3e54cd6 on `config/tagmap.json`: `sizeM` of **three** tags (584, 585, 586) from 0.198 to 0.20; 583 was already at 0.20. In the shared PnP the size acts only via the corners (about 1 mm), but the positions come from a survey with the same scale error (`place_tags`). How much the old map was distorted has not been recalculated. Frontend and backend were not updated (0.198 in `moduleCatalog.ts:428-429`; backend JSON 0.2 with old positions).
